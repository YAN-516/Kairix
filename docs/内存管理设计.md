# Kairix 内存管理设计梳理

本文基于当前仓库实现，说明 Kairix 内核中物理页分配、页表、VMA/VMSet、缺页处理、懒分配、COW、Page Cache、`mmap`、内存回收与 swap 之间的关系。

文档重点是当前代码实际上怎样工作。对于尚未形成完整 Linux 语义的部分，会在“当前边界与注意事项”中单独说明。

## 1. 总体架构

Kairix 的内存管理可以分成五层：

```text
用户态虚拟地址
       │
       ▼
UserVMSet + UserMapArea
描述地址范围、权限、映射类型和后备对象
       │
       ▼
Page Fault / mmap / brk / fork / munmap
决定何时分配、共享、复制或释放页面
       │
       ▼
PageTable + PTE + TLB
建立 VPN → PPN 的硬件可见映射
       │
       ▼
FrameTracker + BuddyFrameAllocator
管理物理页的所有权与生命周期
       │
       ▼
Page Cache / Writeback / Reclaim / Swap
管理文件页共享、脏页写回和内存压力
```

几个核心对象的关系是：

| 对象 | 作用 |
|---|---|
| `PageTable` | 硬件可见的虚拟页到物理页映射 |
| `UserMapArea`，即 VMA | 描述一段连续虚拟地址范围的语义 |
| `UserVMSet` | 一个进程完整的用户地址空间 |
| `FrameTracker` | 一个物理页的 RAII 所有权对象 |
| `Page` | Page Cache 中一个文件页或 tmpfs 页的状态 |
| `SwapSlot` | tmpfs 页面换出后在交换文件中的位置 |

主要源码入口：

- [os/src/mm/mod.rs](../os/src/mm/mod.rs)
- [os/src/mm/frame_allocator.rs](../os/src/mm/frame_allocator.rs)
- [os/src/mm/vm_area.rs](../os/src/mm/vm_area.rs)
- [os/src/mm/vm_set.rs](../os/src/mm/vm_set.rs)
- [polyhal/polyhal/src/pagetable/mod.rs](../polyhal/polyhal/src/pagetable/mod.rs)
- [os/src/fs/page/pagecache.rs](../os/src/fs/page/pagecache.rs)
- [os/src/mm/reclaim.rs](../os/src/mm/reclaim.rs)
- [os/src/mm/swap.rs](../os/src/mm/swap.rs)

## 2. 启动初始化顺序

主核启动时，内存相关初始化顺序大致为：

```text
静态 64 MiB bootstrap kernel heap
       │
       ▼
初始化物理页分配器
       │
       ▼
允许 kernel heap 按需扩展
       │
       ▼
向 PolyHAL 注册物理页分配接口
       │
       ▼
激活内核页表
       │
       ▼
初始化文件系统
       │
       ▼
创建 /.kairix_swap
```

入口位于 [os/src/main.rs](../os/src/main.rs)，内核堆实现位于 [os/src/mm/heap_allocator.rs](../os/src/mm/heap_allocator.rs)。

内核堆与用户内存不是同一个分配器：

- 内核 `Box`、`Vec`、VFS 对象等使用全局 kernel heap。
- 页表页、用户页、Page Cache 页等最终从物理页分配器获得 `FrameTracker`。
- kernel heap 初始使用静态 64 MiB 区域，之后可以按 32 MiB extent 扩展。
- 动态增长上限为物理内存的四分之一，并保留最低物理页储备。

## 3. 物理页分配

### 3.1 管理范围

物理页分配器从 PolyHAL 提供的可用内存区间初始化：

```text
platform memory ranges
       │
       ├─ 按 4 KiB 页边界对齐
       ├─ 跳过空区间
       └─ 加入 BuddyFrameAllocator
```

初始化前会冻结 PolyHAL 的 early allocator，避免早期分配器与正式物理页分配器重复管理同一页。

当前基本页大小固定为 4 KiB。页表接口也只支持 `MappingSize::Page4KB`，暂未实现 2 MiB 或 1 GiB 大页。

### 3.2 BuddyFrameAllocator

中央物理页分配器是 `BuddyFrameAllocator`：

```text
BuddyFrameAllocator
  ├─ ranges[]          平台提供的物理内存区间
  ├─ buddy_heads[32]   不同 order 的空闲链表
  ├─ frame_states[]    每个物理页的状态
  └─ recycled_count    已回收并进入 buddy 的页数
```

它同时维护两类空闲页：

1. 从未分配过的 fresh pages，通过每个 range 的 `current` 指针顺序取出。
2. 已释放的 recycled pages，通过 buddy 空闲链表拆分和合并。

单页分配优先从已回收的 buddy 块中取页，没有合适块时再从 fresh range 顺序分配。连续物理页分配支持指定页数和对齐页数。

实现见 [os/src/mm/frame_allocator.rs](../os/src/mm/frame_allocator.rs)。

### 3.3 每 CPU 缓存

为了减少全局 buddy 锁竞争，物理页分配器前面还有每 CPU 缓存：

| 缓存 | 容量 | 用途 |
|---|---:|---|
| 普通释放页缓存 | 64 页/CPU | 快速复用刚释放的物理页 |
| 匿名 dirty 页缓存 | 16 页/CPU | 批量取得待清零匿名页 |
| 匿名 zeroed 页缓存 | 64 页/CPU | 空闲 CPU 预清零，降低缺页延迟 |

普通释放路径先把页面放入当前 CPU 的缓存。缓存满时，一次把一半页面归还中央 buddy。

匿名缺页优先取得预清零页；没有时才同步清零。调度器空闲阶段可以每次预清零一页，其他 CPU 也可以窃取这些页面使用。

### 3.4 FrameTracker 生命周期

`FrameTracker` 是物理页的 RAII 所有权对象：

```rust
pub struct FrameTracker {
    pub ppn: PhysPageNum,
    allocation_site: &'static Location<'static>,
}
```

普通 `FrameTracker::new` 会清零完整物理页，保证旧数据不会泄露给新的用户映射。`frame_alloc_copy_from` 用于 COW 和私有文件页复制，可以直接复制有效内容并清零尾部。

当最后一个 `FrameTracker` 被释放时，`Drop` 自动把 PPN 归还物理页分配器。需要共享物理页的地方统一使用 `Arc<FrameTracker>`：

```text
Arc strong_count == 1  → 只有当前对象拥有该物理页
Arc strong_count > 1   → COW、mmap、Page Cache 或共享内存仍在引用
```

定义见 [polyhal/polyhal/src/components/common.rs](../polyhal/polyhal/src/components/common.rs)。

### 3.5 分配失败与回收

普通物理页分配失败后的顺序是：

```text
本 CPU 空闲页缓存
  → 中央 BuddyFrameAllocator
  → 排空全部 CPU 页缓存和匿名页缓存
  → 再次分配
  → 回收干净磁盘 Page Cache
  → 换出 tmpfs Page Cache
  → 最后一次分配
  → 仍失败则返回 None / 进入 OOM 路径
```

回收入口见 [os/src/mm/reclaim.rs](../os/src/mm/reclaim.rs)。

## 4. 页表映射

### 4.1 PageTable 结构

`PageTable` 由 PolyHAL 提供跨架构统一接口：

```rust
pub struct PageTable {
    pub root_ppn: PhysPageNum,
    pub frames: Vec<FrameTracker>,
}
```

- `root_ppn` 是根页表物理页。
- `frames` 持有中间页表页，保证页表页生命周期覆盖整个 PageTable。
- RISC-V 和 LoongArch 当前都使用三级、每级 512 项、4 KiB 基本页的页表布局。
- 架构相关的 PTE 编码、页表寄存器和 TLB 操作分别位于 `riscv64.rs` 与 `loongarch64.rs`。

### 4.2 建立映射

建立一个用户页映射时：

```text
输入 VPN、PPN、R/W/X/U 权限
       │
       ▼
按 VPN 的三级索引遍历页表
       │
       ├─ 中间页表不存在
       │      → 分配 FrameTracker
       │      → 创建 table PTE
       │
       ▼
找到叶子 PTE
       │
       ▼
写入 PPN 和架构相关 PTEFlags
       │
       ▼
按需刷新本地或远端 TLB
```

`map_page()` 会完成必要的 TLB 失效；`map_page_no_flush()` 用于批量建表或尚未激活的地址空间，调用者必须负责最后的 TLB 发布。

### 4.3 权限层次

内核中有三层相关权限表示：

| 层次 | 类型 | 含义 |
|---|---|---|
| 系统调用 ABI | `PROT_READ/WRITE/EXEC` | 用户传入的 mmap/mprotect 权限 |
| VMA | `MapPermission` | 内核期望的 R/W/X/U/G/Cache 语义 |
| 页表 | `MappingFlags/PTEFlags` | 架构实际编码 |

VMA 权限与当前 PTE 权限不一定始终相同。例如：

- COW VMA 保留逻辑写权限，但 PTE 临时只读。
- 可写文件 `MAP_SHARED` VMA 保留 W，但初始 PTE 去掉 W，以捕获第一次写并标脏。

因此判断一个地址是否合法，应先看 VMA；PTE 反映的是当前硬件映射状态。

### 4.4 解除映射与 TLB

解除映射时必须遵守：

```text
清除 PTE
  → 对所有可能运行该地址空间的 CPU 做 TLB shootdown
  → 等待失效完成
  → 最后释放 FrameTracker
```

如果先释放物理页，其他 CPU 的旧 TLB 仍可能访问已经被重新分配的页面。批量 `munmap`、COW 权限修改和 `fork` 都显式处理了这一顺序。

## 5. VMA 与 VMSet

### 5.1 UserMapArea（VMA）

`UserMapArea` 描述一段连续虚拟地址范围：

```text
UserMapArea
  ├─ va_range                  虚拟地址范围
  ├─ map_perm                 VMA 逻辑权限
  ├─ area_type                ELF/Heap/Stack/Mmap/Shm/...
  ├─ data_frames              已驻留 VPN → Arc<FrameTracker>
  ├─ lazy_flag                是否仍有未实例化页面
  ├─ cow_flag                 是否需要 COW
  ├─ map_file                 文件后备对象
  ├─ file_offset              VMA 起点对应的文件偏移
  ├─ flags                    MAP_PRIVATE/MAP_SHARED
  ├─ shared_anonymous         匿名 MAP_SHARED 后端
  └─ growdown_flag            MAP_GROWSDOWN
```

`area_type` 当前包括：

- `Elf`
- `Heap`
- `Stack`
- `TrapContext`
- `RtSigreturnTrampoline`
- `Mmap`
- `Shm`

VMA 的核心职责是描述“这段地址应该是什么”，而不是保证每一页已经存在。

定义见 [os/src/mm/vm_area.rs](../os/src/mm/vm_area.rs)。

### 5.2 UserVMSet

`UserVMSet` 表示一个完整进程地址空间：

```rust
pub struct UserVMSet {
    pub page_table: PageTable,
    pub areas: Vec<UserMapArea>,
    ...
}
```

它负责：

- 保存和激活进程页表；
- 按虚拟地址排序保存 VMA；
- 查找地址所属 VMA；
- 为 `mmap` 查找空闲虚拟区间；
- 插入、拆分、合并和删除 VMA；
- 处理懒分配和 COW；
- 在 `fork` 时构造子进程地址空间；
- 在退出时释放用户页和页表页。

`data_frames` 与 PTE 的关系是：

```text
VMA.data_frames 负责物理页所有权
PTE             负责让 CPU 能访问该物理页
```

仅删除 PTE 不一定释放页面；仅删除 `data_frames` 而没有先清 PTE 和刷新 TLB 则不安全。

实现见 [os/src/mm/vm_set.rs](../os/src/mm/vm_set.rs)。

## 6. 用户缺页处理

用户访问没有有效映射或权限不足时，Trap 层将异常分类为：

- Load Page Fault → `AccessType::Read`
- Store Page Fault → `AccessType::Write`
- Instruction Page Fault → `AccessType::Execute`

入口见 [os/src/trap/mod.rs](../os/src/trap/mod.rs)。

整体分派逻辑是：

```text
Page Fault
  │
  ├─ 文件后备 mmap/ELF？
  │      → 专用 file-backed fault 路径
  │
  ├─ 已有只读 PTE 且 VMA 是 COW？
  │      → COW fault
  │
  ├─ PTE 不存在但 VMA 合法？
  │      → lazy allocation fault
  │
  ├─ MAP_SHARED 文件页首次写？
  │      → 标脏并开放 PTE.W
  │
  ├─ 栈允许向下扩展？
  │      → 扩展 VMA 并分配当前页
  │
  └─ 无 VMA或权限不匹配
         → SIGSEGV/SIGBUS 对应错误
```

`PageFaultError` 区分：

| 错误 | 用户态语义 |
|---|---|
| `Normal` | 缺页已修复，重试指令 |
| `InvalidAddress` | 无效地址，通常 SIGSEGV |
| `InvalidMapping` | 映射状态无效 |
| `BeyondFileSize` | 文件 mmap 越过 EOF，通常 SIGBUS |
| `OutOfMemory` | 物理页分配失败 |

## 7. 懒分配

### 7.1 基本策略

堆、栈和普通 mmap 大多以 `lazy_flag = true` 建立：

```text
创建 VMA
  → 不分配全部物理页
  → 不建立全部叶子 PTE
  → 首次访问某个 VPN
  → 只实例化这一页
```

优点是：

- 大虚拟映射不会立即消耗同等大小的物理内存；
- `fork` 不需要补齐尚未访问的页；
- 进程只为实际触碰的页面付出分配和清零成本。

当 `data_frames.len()` 覆盖整个 VMA 后，`lazy_flag` 才会清除。

### 7.2 匿名页

匿名 Heap、Stack、`MAP_PRIVATE|MAP_ANONYMOUS` 首次缺页时：

```text
VMA 权限检查
  → 分配或取得预清零 FrameTracker
  → 插入 data_frames[vpn]
  → 建立 PTE
  → 必要时同步指令缓存
  → 刷新 TLB
```

匿名 `MAP_SHARED` 使用 `SharedAnonymousFrames` 作为稀疏共享后端。即使页面在 `fork` 时尚未分配，父子进程之后首次访问同一页号时，也会发布并使用同一个物理页。

### 7.3 文件页

文件后备 VMA 首次缺页时不分配普通零页，而是计算：

```text
offset_in_area = (fault_vpn - area.start_vpn) * PAGE_SIZE
file_offset    = area.file_offset + offset_in_area
page_id        = file_offset / PAGE_SIZE
```

然后从文件的 Page Cache 获得物理页。普通 mmap 访问越过文件大小时返回 `BeyondFileSize`，不会自动变成匿名零页。

## 8. COW

### 8.1 fork 时

`fork` 不立即复制所有私有物理页：

```text
父进程可写私有页
       │
       ├─ 父子 data_frames 共享 Arc<FrameTracker>
       ├─ 父 VMA 和子 VMA 设置 cow_flag
       ├─ 父 PTE 去掉 W
       └─ 子 PTE 也去掉 W
```

只处理已经驻留的页面。尚未懒分配的匿名页由父子之后分别分配。

`MAP_SHARED` 和 SysV SHM 不进入私有 COW：已驻留页直接共享。匿名 `MAP_SHARED` 还共享 `SharedAnonymousFrames` 后端。

实现见 `UserVMSet::from_existed_user_cow`，位于 [os/src/mm/vm_set.rs](../os/src/mm/vm_set.rs)。

### 8.2 写缺页时

写 COW 页时：

```text
Store Page Fault
  → 找到 VMA 和旧 FrameTracker
  → 检查 Arc strong_count
       │
       ├─ == 1：已独占，不复制，只恢复 PTE.W
       │
       └─ > 1：分配新页，复制 4 KiB，替换 data_frames[vpn]
  → 更新 PTE
  → 多核 TLB shootdown
```

这同时覆盖：

- `fork` 后的匿名私有页；
- 文件 `MAP_PRIVATE` 的第一次写；
- 其他可写私有 VMA 的共享页。

### 8.3 文件 MAP_PRIVATE

文件 `MAP_PRIVATE` 初始读取可以直接共享 Page Cache：

```text
Page Cache frame
  ├─ 进程 A 私有映射，只读/COW PTE
  └─ 进程 B 私有映射，只读/COW PTE
```

第一次写时复制成进程私有页。之后：

- 不再修改 Page Cache；
- 不写回原文件；
- 不影响其他进程；
- `msync` 不会把私有修改同步到文件。

如果某页第一次访问就是写，文件缺页路径会直接从 Page Cache 复制出私有页。

## 9. Page Cache

### 9.1 定位

Page Cache 是“文件页到共享物理页”的全局索引：

```text
(filesystem-tagged inode_id, page_id)
                  │
                  ▼
          Arc<RwLock<Page>>
                  │
                  ▼
          Arc<FrameTracker>
```

普通 `read/write` 与文件 `mmap` 使用同一份文件页物理内存。

### 9.2 分片与键

全局 `PAGE_CACHE` 分为 64 个 shard。每个 shard 独立维护：

```text
cache:     (inode_id, page_id) → Page
lru_order: generation → key
lru_gen:   key → generation
```

inode id 带文件系统标签：

| 文件系统 | 标签 |
|---|---:|
| tmpfs | 1 |
| FAT32 | 2 |
| ext4 | 3 |

同一个 inode 的所有页固定落入同一 shard，便于 truncate、写回和 inode 级扫描。

实现见 [os/src/fs/page/pagecache.rs](../os/src/fs/page/pagecache.rs)。

### 9.3 Page 状态

`Page` 保存：

```rust
struct Page {
    frame: Option<Arc<FrameTracker>>,
    swap_slot: Option<SwapSlot>,
    dirty: bool,
    dirty_generation: usize,
}
```

磁盘文件页通常有 resident frame；tmpfs 页被换出后可以只保留 `swap_slot`。

`dirty_generation` 用于防止 truncate 等操作之后，旧写回任务覆盖新的文件状态。

### 9.4 Cache miss

典型读取流程：

```text
查询 (inode_id, page_id)
  ├─ 命中：更新 LRU，返回 Page
  └─ 未命中：
       分配 FrameTracker
       从文件系统读取 4 KiB
       文件尾部清零
       insert_page_if_absent
       返回最终缓存页
```

并发加载同一页时，先插入的候选页获胜，其他候选 `FrameTracker` 自动释放。

ext4 还实现：

- 普通顺序预读 8 页；
- mmap 缺页预读 16 页；
- stride 预读 4 页。

### 9.5 普通 read/write

普通文件读取：

```text
read
  → 查询或载入缓存页
  → 从 FrameTracker 复制到用户缓冲区
```

普通文件写入：

```text
write
  → 查询或创建缓存页
  → 修改物理页
  → dirty = true
  → 文件进入延迟写回队列
```

tmpfs 的数据本身完全由 Page Cache 承载；FAT32/ext4 的 Page Cache 只是磁盘文件数据的内存副本。

### 9.6 容量和 LRU

磁盘文件 Page Cache 目标上限为：

```text
总物理页 / 4
下限 4096 页，约 16 MiB
上限约 4 GiB
```

tmpfs 不计入这个磁盘缓存上限。

为减少热点锁和有序树操作，同一页面不会每次命中都更新 LRU；页面至少老化约 256 次 shard 访问后才重新 touch。

## 10. mmap

### 10.1 建立阶段

`sys_mmap(start, len, prot, flags, fd, offset)` 的主要流程：

```text
校验 len、offset、flags 和文件权限
  → len 按页向上对齐
  → MAP_FIXED 或查找空闲虚拟区间
  → 构造 UserMapAreaType::Mmap
  → 保存 map_file/file_offset/PRIVATE|SHARED
  → 默认保持 lazy，不建立全部 PTE
  → 返回映射起始地址
```

入口见 [os/src/syscall/mm.rs](../os/src/syscall/mm.rs)。

`MAP_FIXED_NOREPLACE` 在重叠时返回 `EEXIST`；`MAP_FIXED` 会先裁剪原有 VMA。`MAP_POPULATE` 会主动逐页执行一次读缺页处理。

文件映射要求文件可读；可写 `MAP_SHARED` 还要求 fd 可写，并检查 `F_SEAL_WRITE`。

### 10.2 四种主要组合

| 类型 | 首次缺页 | fork 后 | 写入结果 |
|---|---|---|---|
| 匿名 PRIVATE | 分配零页 | 驻留页 COW，未驻留页独立分配 | 进程私有 |
| 匿名 SHARED | 从共享后端取得或分配零页 | 已驻留和未来页面都共享 | 共享内存 |
| 文件 PRIVATE | 读取时共享 Page Cache | 私有写入 COW | 不写回文件 |
| 文件 SHARED | 直接映射 Page Cache | 共享同一文件页 | 标脏并写回文件 |

### 10.3 文件缺页和 fault-around

文件 mmap 缺页时：

```text
VA → VMA 内偏移 → file_offset → page_id
   → File::get_cache_frame(page_id)
   → Page Cache miss 时读盘
   → VMA.data_frames 持有同一个 FrameTracker
   → 建立用户 PTE
```

ext4 的 demanded page 可以触发 16 页向前预读。MM 随后只把已经驻留的连续缓存页批量安装为 PTE；`get_cached_frame` 不分配也不读盘。

### 10.4 文件 MAP_SHARED 脏页追踪

可写文件 `MAP_SHARED` 使用第一次写保护：

```text
VMA 权限：R/W
初始 PTE：R/-
       │
第一次 store
       ▼
Store Page Fault
       │
       ├─ 标记 Page Cache 页 dirty
       ├─ 文件进入 WRITEBACK_QUEUE
       ├─ PTE 恢复 W
       └─ 多核 TLB shootdown
```

如果该页第一次访问就是写，载入页面时直接标脏并建立可写 PTE。

### 10.5 munmap 和 msync

`munmap` 支持：

- 删除完整 VMA；
- 裁掉 VMA 前缀并调整 `file_offset`；
- 裁掉 VMA 后缀；
- 从中间挖空并拆成左右两个 VMA。

解除映射时会先保留被删除的 `FrameTracker`，清除 PTE 并完成 TLB shootdown 后才真正释放。文件 `MAP_SHARED` 的驻留页会重新标脏并加入 writeback。

`msync` 当前只处理文件 `MAP_SHARED`：遍历重叠 VMA 的驻留页、标记 Page Cache dirty，然后调用 `file.flush()`。

## 11. 延迟写回

`WRITEBACK_QUEUE` 保存需要写回的文件引用：

```text
修改 FAT32/ext4 缓存页
  → Page.dirty = true
  → 文件进入 WRITEBACK_QUEUE
  → syscall 返回路径按预算处理
  → file.flush_pages()
  → 写回成功后清 dirty
```

当前策略：

- 默认每次 syscall return 最多写回 8 页；
- 普通脏页延迟周期约 5 秒；
- 内存压力下预算提高到 512 页；
- `fsync`、`sync` 和 `msync` 可以触发显式刷新；
- ext4 通过 `dirty_generation` 避免旧脏页覆盖 truncate 后的新状态。

实现见 [os/src/fs/writeback.rs](../os/src/fs/writeback.rs)。

脏页不能直接回收，因此 Page Cache 可以暂时超过目标上限，直到 writeback 把页面变为干净页。

## 12. 内存回收

空闲物理页水位线是：

| 水位 | 页数 | 作用 |
|---|---:|---|
| Low | 16384 | 低于此值请求后台写回/回收 |
| High | 32768 | 持续推动到该目标附近 |

回收磁盘 Page Cache 页需要同时满足：

- 后端是 FAT32 或 ext4；
- 页面干净；
- 页锁可以取得；
- `Page` 没有外部借用；
- resident `FrameTracker` 没有被 VMA/mmap 等对象引用。

满足后删除缓存条目，最后一个 `FrameTracker` 析构并归还物理页。

后台低水位路径主要执行脏页写回和干净缓存裁剪；tmpfs 换出主要出现在物理页分配失败后的同步兜底路径。

## 13. Swap

### 13.1 当前定位

当前 swap 是专用于 tmpfs Page Cache 的最小实现，不是完整 Linux 式匿名页 swap。

可以换出：

- 没有外部 frame 引用的 tmpfs Page Cache 页。

不能换出：

- Heap、Stack 和匿名 PRIVATE mmap；
- 普通 COW 私有页；
- 被 mmap/VMA 持有的 tmpfs 页；
- 内核内存。

### 13.2 交换文件

根文件系统挂载完成后创建：

```text
/.kairix_swap
逻辑容量：128 MiB
页面大小：4 KiB
槽数量：32768
```

`SwapState` 保存文件引用、空闲槽列表和槽总数。文件创建失败时 swap 被禁用，但内核继续启动。

### 13.3 换出

```text
Page {
    frame: Some(frame),
    swap_slot: None
}
       │
       ├─ 必须属于 tmpfs
       ├─ 必须取得页面写锁
       ├─ Arc::strong_count(frame) == 1
       └─ 分配空闲 SwapSlot
       │
       ▼
通过 write_at_direct 写入 4 KiB
       │
       ▼
Page {
    frame: None,
    swap_slot: Some(slot)
}
       │
       ▼
释放物理页
```

direct I/O 避免 swap 文件写入再次进入 Page Cache。

### 13.4 换入

tmpfs read/write 或新的文件 mmap 缺页调用 `Page::ensure_resident()`：

```text
frame == None
  → 分配新物理页
  → 从 SwapSlot direct read
  → 释放槽
  → frame = Some(new_frame)
  → swap_slot = None
```

被换出的 `Page` 因 truncate 或文件删除而销毁时，`Drop` 会自动归还尚未使用的 SwapSlot。

## 14. fork 后各类页面的语义

| 页面来源 | fork 时已驻留 | fork 时未驻留 |
|---|---|---|
| Heap/Stack/匿名 PRIVATE | 父子共享 frame，PTE 只读，写时 COW | 父子之后各自分配 |
| 匿名 SHARED mmap | 父子直接共享 frame | 共享 `SharedAnonymousFrames`，以后仍取得同一页 |
| 文件 PRIVATE mmap | 共享 Page Cache 或已有私有页按 COW | 读取时共享 Page Cache，写时私有复制 |
| 文件 SHARED mmap | 父子直接共享 Page Cache frame | 之后缺页仍取得同一缓存页 |
| SysV SHM | 直接共享 | 按共享后端语义处理 |

## 15. 关键不变量

维护该模块时，需要保持以下不变量：

1. 用户可观察到的新匿名页必须完整清零。
2. `data_frames` 持有已驻留用户页的生命周期；PTE 本身不拥有物理页。
3. 释放用户 frame 前必须先清 PTE，并完成相关 CPU 的 TLB shootdown。
4. COW frame 引用数大于 1 时不得建立可写别名。
5. 文件 `MAP_PRIVATE` 的写入不得修改 Page Cache。
6. 文件 `MAP_SHARED` 在开放 PTE.W 前必须先标记 Page Cache dirty。
7. 被 mmap 持有的 Page Cache frame 不能从缓存索引中直接删除。
8. tmpfs 页面只有在交换写入成功后才能释放 resident frame。
9. swap 文件 I/O 必须绕过 Page Cache，避免递归回收。
10. VMA 拆分时必须同步调整文件偏移和匿名共享后端偏移。

## 16. 当前边界与注意事项

### 16.1 通用 swap 尚未实现

匿名进程页没有 PTE swap entry，也没有匿名页换出/换入缺页路径。当前实现只能释放未被 mmap 引用的 tmpfs Page Cache 页。

### 16.2 用户态 swap 统计尚未接通

`/proc/meminfo` 和 `sysinfo()` 仍报告 `SwapTotal/SwapFree = 0`；`mlock/munlock` 中也保留了“不支持 swap”的旧注释和简化语义，与内核内部已有的 tmpfs swap 不完全一致。

### 16.3 mmap flags 校验

`sys_mmap` 当前只检查 `MAP_SHARED` 和 `MAP_PRIVATE` 至少出现一个，没有拒绝两者同时设置。两者同时存在时，后续解析会落入默认的 `MAP_PRIVATE` 分支。

### 16.4 MAP_FIXED 覆盖共享映射

普通 `munmap` 会在删除文件 `MAP_SHARED` 映射前快照驻留页，并在解除映射后重新标脏、加入 writeback。`MAP_FIXED` 覆盖旧范围时直接裁剪 VMA，目前没有同等的共享页快照步骤，存在遗漏最后一次重新标脏的风险。

### 16.5 msync 标志语义

`MS_ASYNC`、`MS_SYNC`、`MS_INVALIDATE` 已进行参数校验，但当前最终路径都会调用 `file.flush()`，同步与异步行为还没有真正区分。

### 16.6 页缓存和 swap 回收限制

- dirty 磁盘页在写回前不能回收，缓存可以暂时超过上限。
- 被 VMA 持有的文件缓存页不能直接回收。
- 被 mmap 持有的 tmpfs 页不能换出。
- tmpfs 换出主要是物理页分配失败后的兜底，不是主动后台换页。

### 16.7 仅支持 4 KiB 基本页

`MappingSize` 当前只有 `Page4KB`，尚未提供大页、透明大页或 huge mmap。

## 17. 典型访问的完整路径

### 17.1 匿名堆第一次写

```text
用户写 heap VA
  → Store Page Fault
  → UserVMSet 找到 Heap VMA
  → 检查 W 权限
  → 取得清零 FrameTracker
  → data_frames[vpn] = frame
  → map_page(vpn, ppn, U|R|W)
  → 刷新 TLB
  → 重试用户指令
```

### 17.2 fork 后写匿名页

```text
父子共享 Arc<FrameTracker>
  → PTE 均为只读
  → 一方写入触发 Store Page Fault
  → strong_count > 1
  → 分配并复制新页
  → 当前进程 data_frames 替换为新 frame
  → 当前 PTE 恢复 W
  → TLB shootdown
```

### 17.3 文件 MAP_PRIVATE 第一次写

```text
文件 VMA
  → 从 Page Cache 取得文件 frame
  → 复制到私有 frame
  → 建立可写私有 PTE
  → 后续修改不进入 writeback
```

### 17.4 文件 MAP_SHARED 先读后写

```text
读缺页
  → Page Cache frame
  → 建立只读 PTE
  → 用户读取成功

第一次写
  → 写保护 fault
  → Page Cache 标脏
  → 文件加入 WRITEBACK_QUEUE
  → PTE 开放 W
  → 后续写直接修改缓存 frame
  → 延迟写回文件
```

### 17.5 tmpfs 页面换出再读取

```text
物理页分配失败
  → 回收磁盘干净缓存仍不足
  → 选择无外部引用的 tmpfs 页
  → 写入 /.kairix_swap
  → 释放 frame

之后 read(tmpfs)
  → ensure_resident
  → 分配新 frame
  → 从 SwapSlot 读回
  → 释放 SwapSlot
  → 返回文件数据
```

## 19. 总结

当前 Kairix 内存管理的主线可以归纳为：

```text
VMA 描述地址空间语义
  → Page Fault 按需实例化页面
  → PageTable 向硬件发布映射
  → FrameTracker 管理物理页生命周期
  → COW 延迟私有页复制
  → Page Cache 统一文件 read/write/mmap
  → Writeback 处理磁盘脏页
  → Reclaim 回收干净文件页
  → Swap 为无外部引用的 tmpfs 页提供后备
```

它已经具备懒分配、fork COW、文件和匿名 mmap、共享匿名后端、统一 Page Cache、延迟写回、LRU 回收以及 tmpfs swap。当前最明显的扩展方向是通用匿名页 swap、更完整的用户态 swap/`mlock` 语义、大页支持，以及补齐少数 mmap 边界路径。
